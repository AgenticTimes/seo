# 关键词发现（keyword-discovery）— 模块与目录规划

> 来源：`find_trend.md` 方法论。语言 Go 1.25 / 存储 SQLite / 首轮 = 手动流程工具。
> 本文件是 ddd-hexagonal 工作流的「实现准备」产出，先定模块与目录，再写代码。

## 1. 业务流程分析

主流程（手动 CLI，一轮 = 一个关键词）：

```
配置(地区/时间窗/实体类型)
  → 采集 Related Queries(Top+Rising) + Related Topics
  → 记录发现词（去重、记父节点、记来源）
  → 时间窗验证（30D→90D→12M→5Y）
  → 判定趋势类别
  → 过闸：只有合格词可成为下一轮种子（深度 ≤ 2）
  → 聚类/外部验证 → 机会评估
  → 持久化 + 定期重监控
```

角色：操作者（手动触发每一轮）。触发：人工命令。
成功路径：产出一批 `SeedCandidate` 并写入关键词库。
失败路径：采集失败（网关）、判定证据不足（Insufficient）、词过宽（TooBroad）、重复（幂等跳过）。

## 2. 业务规则（编号 → 代码落点）

| 编号 | 规则 | 判定/约束 | 落点 |
|---|---|---|---|
| BR-01 | 时间窗交叉验证 | 30D↑∧90D↑∧12M平稳→Emerging；30D↑∧90D↑∧12M↑→Sustained；5Y持续→LongTerm；30D↑∧12M无变化→ShortLived；30D↓→Declining；窗口缺失→Insufficient | `domain/hotsearch` `Keyword.AssessTrend` |
| BR-02 | Breakout ≠ 热度 | Breakout 只标记相对增长>5000%，不参与绝对热度排序 | `domain/hotsearch` `DiscoverySource` |
| BR-03 | 增长 ≠ 机会 | 机会需叠加 需求具体性×产品化×竞争 | `evaluation/domain/opportunity` `Opportunity.Assess` |
| BR-04 | 宽泛词强制下钻 | 判定 TooBroad 的词不得成为机会；人工确认 | `Keyword.MarkTooBroad` |
| BR-21 | 过宽建议 | 单词无修饰 + 子词无共同主题 → 建议过宽，不自动关闭 | `SuggestTooBroad` + `query.Advisor` |
| BR-05 | 近义簇需收敛 | 簇内必须判为同一需求才可推进机会 | `domain/hotsearch` 内的聚类 `KeywordCluster.AssessCohesion` |
| BR-06 | 归一化指数语义 | 0–100，不可跨窗口/跨词比绝对量；只能比同窗口内趋势形状 | `domain/hotsearch` `TrendIndex`（按窗口绑定，不提供跨窗比较 API） |
| BR-07 | Top/Rising 分工 | 发现新词以 Rising 为主，Top 作成熟度旁证 | `domain/hotsearch` `DiscoverySource` + 采集器职责 |
| BR-08 | Topic 优先 | 同时提供 Topic/Search term 时选 Topic | `shared/kernel` `EntityType` + 采集请求构造 |
| BR-09 | 扩展深度 ≤ 2 | depth ∈ [0, MaxDepth] | `domain/hotsearch` `ExpansionPolicy` |
| BR-10 | 种子准入 | 仅 trend-verdict ∈ {Emerging, Sustained} 且未 TooBroad 且未超深度 | `application/command/promote` 闸门 |
| BR-11 | 趋势 ≠ 付费意愿 | 机会 Approve 前必须有外部证据 | `evaluation` `Opportunity.AttachEvidence` |
| BR-20 | 机会准入 | 趋势合格 + 不过宽 + 至少一条证据才可批准 | `Opportunity.Approve(gate)` |
| BR-12 | 季节优先 | 季节强度 ≥ 0.30 时改看结构增长，不看 30D 环比 | `hotsearch.Signals` + `classifyTrend` |
| BR-13 | 结构增长 | 去季节后趋势项 > 0 才算结构性增长 | `hotsearch.Decompose` |
| BR-14 | 动量 | 30D / 90D 对数斜率及加速度作为信号 | `hotsearch.ComputeSignals` |
| BR-15 | 尖峰过滤 | max/median ≥ 3 且 90D 未涨 → 事件 | `Signals.IsSpike` |
| BR-16 | 噪声门槛 | 30D 采样点 < 7 → 数据不足 | `Signals.Noisy` |
| BR-17 | 意图分类 | 导航/交易/商业/信息，规则判定 | `hotsearch.ClassifyIntent` |
| BR-18 | 品牌词/红海 | 标记品牌词；父节点聚合子词算品牌占比 | `IsBrandMention` + `AnalyzeChildren` |
| BR-19 | 语言偏移 | 非拉丁占比 ≥ 30% 提示换 geo | `Signals.NonLatinRatio` |

阈值（growth、窗口最小样本、MaxDepth=2）全部进 Policy VO，不写死。

## 3. 限界上下文（战略设计）

| 上下文 | 职责 | 不负责 | 聚合 |
|---|---|---|---|
| `discovery` | 种子扩展、相关词采集、趋势观测与验证、聚类 | 商业价值判断、付费验证 | Keyword、KeywordCluster |
| `evaluation` | 搜索意图、产品化方向、竞争、外部证据、机会决策 | 趋势数据采集与归一化 | Opportunity |

关系：
- `evaluation` 是 `discovery` 的**下游**，通过发布语言（`KeywordKey`、`TrendVerdict`）读取，不反向依赖。
- 跨上下文闸门（BR-10/BR-11）放在 **application** 编排层，不写跨上下文的 Domain Service——避免 domain 互相 import。
- Google Trends 是**防腐层（ACL）**，不是上下文：`infrastructure/trends` 的 mapper 负责把外部原始数据译为领域 VO，并在边界强制 BR-06/BR-08。

共享内核只放无规则的基础 VO：`Term`、`Country`、`EntityType`。

## 4. 聚合设计（战术设计）

### 4.1 Keyword（discovery，聚合根）

- 身份 `KeywordKey{Term, Country, EntityType}` —— 自然键即 ID，天然幂等去重。
- 字段：key、parentKey（seed 为空）、depth、source、discoveredAt、pipelineState、tooBroad、observations（每窗口至多一条，当前快照）、verdict、clusterID。
- 不变量：同窗口观测唯一；`0 ≤ depth ≤ policy.MaxDepth`；未验证不得进 SeedCandidate。
- 根方法（业务动词，非 setStatus）：
  - `RecordObservation(obs)` — 写入/替换某窗口观测
  - `AssessTrend(policy) TrendVerdict` — BR-01
  - `MarkTooBroad(reason)` — BR-04
  - `ConfirmAsSeedCandidate(policy)` — BR-09/BR-10 的领域侧校验
  - `AttachCluster(id)`
  - `Discard(reason)` / `ReopenForRevalidation()`
- 状态机：`Discovered → Validated → SeedCandidate`，分支 `TooBroad`、`Discarded`；`Reopen` 回 `Discovered`。

### 4.2 KeywordCluster（discovery，聚合根）

- 字段：id、canonicalTerm、members[]、cohesion。
- 方法：`AddMember`、`Absorb(other)`、`AssessCohesion(judgement)`（BR-05）、`IsCohesive()`。
- 不变量：成员不可跨 entityType/country 混簇。

### 4.3 Opportunity（evaluation，聚合根）

- 字段：id、keywordKey、intent、productization、competition、evidence[]、score、decisionState。
- 方法：`RecordIntent`、`AttachEvidence`（BR-11）、`Assess(policy)`（BR-03）、`Approve(gate)`、`Reject(reason)`。
- 不变量：`Approve` 需要 `gate = {trendValidated, clusterCohesive, hasEvidence}` 全真；gate 由 application 计算后传入（跨上下文解耦）。
- 状态机：`Candidate → EvidenceGathered → Approved | Rejected`。

### 4.4 值对象

`KeywordKey`、`TrendWindow{7D,30D,90D,12M,5Y}`、`TrendIndex`（构造绑定窗口）、`TrendObservation{Window, Start, End, Samples}`、`TrendVerdict`、`DiscoverySource`、`ExpansionPolicy`、`TrendPolicy`、`SearchIntent`、`CompetitionAssessment`、`OpportunityScore`、`Evidence`。

## 11. 运行

假数据（默认，无需网络）：

```bash
go run ./cmd/seotrend -db seo.db
# http://127.0.0.1:8080
```

真实 Google Trends（本机 Chrome，无头）：

```bash
go run ./cmd/seotrend -db seo.db -gateway browser
# 可选参数
#   -chrome <path>        指定浏览器，默认自动探测
#   -headless=false       看到窗口（排查同意页）
#   -trends-proxy http://127.0.0.1:7890   显式代理
#   -chrome-remote off    忽略 9222 上的 Chrome，强制本地起
#   -min-interval 3s      两次 Google 调用之间的最小间隔
#   -trends-base <url>    指向 mock 服务
```

复用已登录 / 已验证的 Chrome（推荐，命中率最高）：

```bash
# 1) 先启动一个可调试的 Chrome。Chrome 136+ 不允许对默认 profile 开调试端口，
#    所以必须给独立的 --user-data-dir。
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --remote-debugging-port=9222 \
  --user-data-dir="$HOME/.seo-chrome" \
  https://trends.google.com/trends/explore

# 2) 如果出现「异常流量 / 人机验证」，在这个窗口手动完成一次。
#    保持窗口打开。

# 3) 启动服务。默认 -chrome-remote=auto，会自动探测 9222 并复用
go run ./cmd/seotrend -db seo.db -gateway browser
```

- `-chrome-remote` 取值：`auto`（默认，9222 有调试 Chrome 就复用，否则本地起）、`off`（总是本地起）、或显式 URL
- 远程模式会忽略 `-headless` / `-chrome` / `-trends-proxy`，连接时只做 `/json/version` 健康检查，不会额外开 `about:blank` 标签页
- 应用关闭时只断开连接，不关闭你的 Chrome

人机验证（CAPTCHA）流程：

1. 你点 ③/④，服务在已连接的 Chrome 里开一个新标签页访问 Trends。
2. Google 把该标签页重定向到 `google.com/sorry`。
3. 服务识别到重定向，**保留该标签页不关**，并返回 `ErrCaptchaRequired`。
4. UI 在详情卡片里显示黄色提示：切到 Chrome → 完成验证 → 回到本页重试。
5. 你完成验证后，重新点刚才那一步。成功后旧验证页自动关闭。
6. 如果标签页被关掉，可点「重新打开验证页」（POST `/verify`）。

注意：无头模式下标签页存在但不可见，所以验证必须用有头 Chrome（`-chrome-remote` 或 `-headless=false`）。

实现要点：

- 浏览器只负责建立会话（cookie / 同意页），数据由页内 `fetch` 调 Trends 内部接口取得，避免抓 SVG。
- 响应前缀可能是 `)]}'` 或 `)]}',`，两种都剥。
- `rankedList` 顺序不稳定，**不按索引取 Top/Rising**，改为按内容分类：含 `%` 或值 >100 记为 Rising，`Breakout`/≥5000 记为 Breakout，其余为 Top；同名条目保留更强的增长信号。
- 序列按 24 点降采样后再入库，BR-01 只需首尾形状。
- 失败映射：429 → 限流；重定向到 `google.com/sorry` → 人机验证；其他跨域落点 → 同意页；`Failed to fetch` → 网络/代理不可达。原始错误写入服务端日志。
- 导航后先检查 `location.href` 是否仍在 Trends 域内，避免在验证页上执行 fetch 后只得到含糊的 "Failed to fetch"。
- 真实接口有 429 和采样波动，适合自用低频；要稳定服务需换官方/付费 API。

## 12. 分析信号（已落地）

每个词在「判定趋势」时计算并持久化一份 Signals 快照：

| 字段 | 含义 | 规则 |
|---|---|---|
| Momentum30 / Momentum90 | 对数斜率，单位：每采样点 | BR-14 |
| Acceleration | 30D − 90D 斜率 | BR-14 |
| SpikeRatio | max / median | BR-15 |
| Seasonality | 季节项方差占比（0–1） | BR-12 |
| StructuralGrowth | 去季节后趋势项相对变化 | BR-13 |
| Intent | 未识别 / 信息 / 商业调研 / 交易 / 导航 | BR-17 |
| BrandMention | 是否命中品牌表 | BR-18 |
| NonLatinRatio | 非 ASCII 字符占比 | BR-19 |
| SevenDayChange | 7D 相对变化，捕捉新闻型突增 | 信号 |
| Reasons | 结论依据代码，UI 翻译成中文 | 可解释性 |
| Points30 / Points90 | 采样点数 | BR-16 |
| BrandShare / ChildCount | 子词中品牌词占比 | BR-18 |

判定顺序变化：30D 噪声门槛 → 方向 → 尖峰过滤 → 季节/结构 → 原窗口交叉验证。
每个结论同时写入 `Reasons`（如 `SUSTAINED`、`SEASONAL_GROWTH`、`SPIKE`），UI 在「结论依据」里逐条解释，7D 变化作为辅助信号展示但不改变判定。
新增判定：`SEASONAL`、`SEASONAL_GROWTH`、`EVENT`；其中 `SEASONAL_GROWTH` 允许进入下一轮。

数据粒度调整：5Y 保留至 260 个周点（STL 需要两个完整周期），30D/90D 保留 30/90 点，12M 52 点；UI 只显示 24 根柱，降采样发生在展示层。

降噪：`-trends-samples N` 让采集层对同一窗口抓 N 次并逐点取中位数；N=3 明显降低采样噪声，但调用次数与耗时同步上升。品牌占比只在判定有子词的节点时计算，子词通过仓储加载后由应用层传入聚合。

## 13. 机会评估（evaluation 上下文，已落地）

聚合：`Opportunity`，以 `hotsearch.Key` 为身份，一个词最多一个机会。

| 状态 | 含义 |
|---|---|
| `CANDIDATE` | 已创建，等待证据 |
| `EVIDENCE_GATHERED` | 至少一条外部证据 |
| `APPROVED` / `REJECTED` | 终态，不可再改 |

规则：

- 创建时拒绝导航型意图（BR-17）与不允许晋级的 verdict（BR-10）
- 证据必须带链接或摘要；同一 URL 不能重复
- 批准需要：趋势合格、词不过宽、证据数 ≥ 1（BR-20）
- 拒绝必须写原因
- 闸门由应用层从 hotsearch 聚合计算后传入，evaluation 不反向依赖用例

用例与落点：

```
internal/evaluation/
  domain/opportunity/          R  聚合、证据、状态、仓储接口
  application/createopportunity  F  幂等创建
  application/attacheevidence    F  追加证据
  application/decideopportunity  F  批准 / 拒绝
  application/query/lookup.go    F  只读查询
```

存储：`0003_opportunities.sql`，证据存 JSON；SQLite 与内存两套实现。

UI：详情页「机会评估（BR-20）」区块，支持创建、添加证据、批准、拒绝，终态后表单消失。

尚未实现：自动采集外部证据（Reddit/竞品/评论）与搜索量/竞争评分；当前证据由人工录入。
